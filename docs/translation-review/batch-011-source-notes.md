## 訂正と照合

- 形式と搬送を区別した。JWTもセッションIDもCookieで送れる。自己完結型トークンのローカル検証と、サーバー側セッションの照会を比較する。
- JWSの署名・MACとJWEの暗号化、公開鍵署名とHMACの鍵の役割、デコードと検証を区別。署名済みでもペイロードが秘密になるとは限らない。
- 署名だけで検証が完了するという原文を訂正。アルゴリズムと鍵、発行者・対象・期限・用途・認可を確認し、採用プロファイルの必須クレームを明示する。汎用JWT仕様のexpは一律必須ではない。
- 失効が不可能という断定を、追加状態を見ないオフライン検証の限界として説明。個別失効、短い期限、鍵全体の無効化、キャッシュや状態配布の遅延を区別。失効リストの採用や更新時の状態管理を一律に失敗とせず、要件とコストを比較する。
- CVE-2015-9256は一次CVE記録でDatto製品の復元マウントポイントのアクセス制御の問題と確認した。JWTのalg:noneの例として引用しない。RFC 8725のnoneとRSA/HMAC混同を区別し、別の攻撃のCVE番号へ機械的に置換しなかった。
- HttpOnlyは値の直接読み取りを防ぐが、同一オリジンの不正コードによる認証済み操作まで防がない。SameSiteも多層防御の一つとして説明し、CSRF・Origin・GETの設計を補った。sessionStorageの短い保存期間もXSS対策とはしない。
- 更新トークンは任意、15分は例。公開クライアント向け更新トークンの送信者束縛またはローテーションの要求を反映。更新時の状態管理と各APIのローカル検証、更新トークン失効と既発行アクセストークンの有効性を分ける。トークン平文のDB保存を必須とはしない。
- OAuthアクセストークンはJWTに限定されず、OIDC IDトークンとは用途が違う。内部ネットワークを理由に検証を省かず、JWT形式だけでパスワード再設定URLがワンタイムにならないことも明記した。
- セッション方式を常に安全・高速とは断定しない。結論の構成選択は要件からの設計判断であり、規格が単一のアーキテクチャを義務付けるという主張ではない。
