# [CopilotとローカルAIの使い分け：データ境界と実測で決める](https://kenji.blog/p/hybrid-ai-development-workflow/)

コード支援AIは、IDE内の補完からエージェント型の編集まで幅広くなりました。選択では「クラウドは高性能、ローカルは安全」と決めつけず、送信されるデータ、契約、実際のタスク品質、遅延、運用費用を確認する必要があります。

この記事は2026年11月23日時点の公式資料に基づく判断方法です。製品、モデル、設定、ポリシーは変わるため、導入時にはリンク先と所属組織のルールを再確認してください。

## クラウドAIとローカル推論の違い

GitHub Copilotなどのクラウド機能は、モデルやIDE機能によって、プロンプト、コード断片、リポジトリの関連情報がサービス側へ送られます。GitHubの現行ポリシーでは、個人向けCopilotプランの利用データがモデルの学習・改善に使われる場合があり、個人設定からオプトアウトできます。一方、Copilot BusinessとEnterpriseの顧客データは、顧客の許可なしに学習へ使わないと説明されています。適用されるプラン、モデルのホスティング先、機能、管理者設定を確認してください。

- [GitHub Copilotの個人向けポリシー](https://docs.github.com/en/copilot/how-tos/manage-your-account/manage-policies)
- [GitHub Copilotモデルのホスティングとデータ取扱い](https://docs.github.com/en/copilot/reference/ai-models/model-hosting)

ローカル推論では、モデルを自分の端末で実行し、推論入力を端末内にとどめられます。ただし「ローカルモデルを選んだ」だけでは完全オフラインとは限りません。IDE拡張のテレメトリー、同期、外部ツール、モデル取得時の通信を確認します。Continueをインターネットから切り離す場合は、拡張機能とモデルを事前に用意し、匿名テレメトリーを無効にする手順があります。

- [Continueをインターネットなしで使う手順](https://docs.continue.dev/guides/running-continue-without-internet)

また、Ollamaにはローカルの`http://localhost:11434`と、APIキーを使うクラウドの`https://ollama.com/api`があります。Ollama経由だからローカル処理とは限りません。接続先を設定で確認し、ローカルサーバーをネットワークへ公開する場合は認証やアクセス制御を別途設計してください。

- [Ollama APIの接続先と利用方法](https://docs.ollama.com/api/introduction)

## 用途とデータ分類から経路を選ぶ

まず組織のデータ分類・AI利用規程を確認し、コード、ログ、設計書、認証情報のどれを外部サービスに送信できるかを決めます。シークレットはローカル・クラウドを問わずプロンプトに含めず、テスト用の値に置き換えてください。クラウドを使う場合は、プラン別の学習利用、保存期間、濫用監視、地域、管理者制御、モデル提供者への転送も確認します。

| 作業の例 | 確認する点 | 候補となる経路 |
| --- | --- | --- |
| 定型コード補完、コメントやテストの下書き | 補完精度、遅延、IDE連携、送信データ | 承認済みクラウド機能または小型ローカルモデル |
| 社内コードの要約・修正 | 入力範囲、根拠の確認、契約と保管条件 | 組織承認済みクラウド、または統制されたローカル環境 |
| 機密・規制対象コード | 外部送信禁止、ログ、ネットワーク境界、監査 | 要件を満たす隔離されたローカル環境。組織の承認が前提 |
| 大規模な設計・複雑なデバッグ | 評価品質、コンテキスト上限、ツール権限、費用 | 要件を満たすクラウドまたは社内ホストモデル |
| インターネット接続のない環境 | 事前取得、拡張機能の通信、更新・脆弱性対応 | 検証済みのオフライン構成 |

表は製品の性能順位ではありません。利用可能な経路を組織のルールとタスク評価で絞り込むための出発点です。

## 品質・遅延・費用を同じタスクで測る

自分の作業から、成功条件、失敗例、評価方法を含む小さなテストセットを作ります。候補モデルには同じコードと指示を与え、モデルID、拡張機能、日付、設定を記録してください。正しさだけでなく、テスト通過、既存設計との一貫性、安全な拒否、手直し時間も比べます。出力のばらつきがあるため複数回試し、重要なコードは開発者がレビューしてテストを実行します。

応答時間は最初の出力までと全体完了を分け、待ち時間を記録します。総費用はクラウドの従量料金だけでなく、契約料、再試行、レビュー、ローカル機器の購入・電力・保守も含めて考えます。ローカルモデルの速度と品質は、モデルサイズ、量子化、コンテキスト長、GPU/メモリー、IDEの設定に左右されます。パラメーター数やVRAMの単一の目安だけで可否を判断せず、手元のハードウェアで確認してください。

## ローカルモデルを試す最小手順

Ollamaをインストールしてから、Ollamaのモデルカタログでライセンス、取得サイズ、機能を確認し、利用するモデルの正確なタグを取得します。

```sh
ollama pull <model-name:tag>
```

Continueの現在の設定形式では、Ollamaを次のように登録できます。`<MODEL_ID>`は`ollama list`に表示される取得済みモデルIDに置き換えます。

```yaml
name: Local coding model
version: 0.0.1
schema: v1
models:
  - name: Local model
    provider: ollama
    model: <MODEL_ID>
    apiBase: http://localhost:11434
    roles:
      - chat
```

モデルのツール呼び出し、画像入力、コンテキスト上限などは個別に異なり、IDEが自動検出しても実際の動作を確認する必要があります。最小権限で始め、ファイル編集やシェル操作を伴うエージェントは、変更確認と人の承認を必須にします。外部ソースコードを含むプロンプトインジェクションにも注意してください。

- [Ollama API](https://docs.ollama.com/api/introduction)
- [ContinueのOllama設定](https://docs.continue.dev/customize/model-providers/top-level/ollama)
- [Ollamaで利用できるモデル](https://ollama.com/library)

## 小さく始め、条件が変われば再評価する

まず低リスクのタスクを選び、承認済みのクラウド機能とローカルモデルを同じ評価セットで比較します。出力品質、手直し時間、遅延、費用、データの送信先を確認したうえで、用途別のルールをチームで決めます。モデル、プラン、拡張機能、契約が更新されたときもポリシーと評価を見直してください。

クラウドかローカルかだけで安全性は決まりません。処理経路を把握し、入力を必要最小限にし、許可された環境で検証することが重要です。
